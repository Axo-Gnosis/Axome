### Evidence: blast radius at 614089b

- **Header parsing fails, including read-only.** SpawnLink.writes now deserializes Option<WriteScope>; each root is typed and each layer is an array. Legacy strings fail deserialization. A legacy [] is explicitly rejected because zero new layers would allow everything, whereas old [] denied everything (axo/crates/axo/src/store/entry.rs:113-136). All header/full-read paths share parse_header; open_write parses before any repair/write, and open_read has no bypass (axo/crates/axo/src/store/jsonl.rs:77-110,150-213). Axo::open_session_read delegates directly (axo/crates/axo/src/axo.rs:248-250). Direct open_session(child_path) fails parsing *before* it can return the normal ChildSession/root redirect (same file:186-197).
- **Listing succeeds, silently drops those children apart from warnings.** JsonlStore::list catches per-file header errors and skips them; it does not abort the directory listing (axo/crates/axo/src/store/jsonl.rs:216-254). Axo::list_sessions simply delegates (axo/crates/axo/src/axo.rs:269-271). Root entries survive. Axome lookup using the returned infos cannot find the skipped child (Axome/src-crates/axome-core/src/services/axo/mod.rs:1770-1779). Consequently a previously indexed child may be visible in cached history yet fail inspection; refreshed discovery cannot expose it through valid SessionInfo.
- **Root open is not poisoned by the bad child.** Its own header/entries still parse. Tree usage seeding reads children but catches errors and contributes zero for an unreadable subtree (axo/crates/axo/src/session/mod.rs:701-737,1716-1737). Root child reconciliation runs in the background after setup; each child's error is logged/skipped rather than returned to the root opener (same file:2174-2182; session/children.rs:417-488). Bad child's unreported runs are not recovered/reported; it is not seeded or revived. Other admitted children continue reconciliation.
- **Axo::session(bad_child_id)** waits for reconciliation, then normally returns SessionNotFound because the failed read happened before seed insertion (axo/crates/axo/src/session/children.rs:229-248,451-487). A preexisting seed whose file subsequently becomes unreadable would instead fail during revival. This is a fresh-process upgrade scenario, not proof that an already-live old-process child suddenly fails.
- **jobs_from_entries(root_header, root_entries) remains usable.** It is pure journal replay, no child file reads (axo/crates/axo/src/jobs/mod.rs:507-519). Root ChildStart/JobEnd entries remain available, so historical child job rows can survive even though the child transcript cannot open. Calling it for the bad child through the ordinary read path is impossible because obtaining that child's Header fails first.
- **tree_usage becomes partial, not an opening error.** Root own usage and readable subtrees survive; each unreadable child and its whole subtree count as zero, even if root JobEnd rollups existed (axo/crates/axo/src/session/mod.rs:701-737,762-768,1723-1737). Axome's closed-session reconstruction independently follows the same policy, warning and adding zero (Axome/src-crates/axome-core/src/services/axo/mod.rs:1782-1839,1847-1869). Thus “only opening that child breaks” understates the impact: listing loses children, reconciliation loses them, and usage is understated, while roots remain accessible.

### Evidence: conversion semantics and upstream intent

Old normalized strings were absolute paths or registered scheme prefixes; old effective_writes flattened intersections by keeping the narrower overlapping root. Old writes::within explicitly considered filesystem paths and URLs disjoint, even if a URL resolved to that filesystem location (axo at 0f4f890^, crates/axo/src/tools/writes.rs:15-74; inspected with git show). The persisted list is already the **effective flattened ceiling**, not raw unexpanded frontmatter.

New WriteScope is a transparent array of layers; each layer ORs roots, all layers must permit the target. Normalization turns relative paths into absolute paths against cwd, keeps registered URLs symbolic, trims URL trailing slashes, and drops invalid/unknown inputs. File targets compare canonicalized real paths; URL roots resolve through the **current session's scheme registry** at check time. Virtual targets use same-scheme segment-prefix matching, reject '..', and cannot match Path roots. In particular local:// means the child's own local directory, not the parent's (axo/crates/axo/src/tools/writes.rs:12-55,59-70,97-140; session/policy.rs:49-74).

For **valid old normalized roots**, wrapping the old OR-list in **one layer** and typing absolute strings as Path, scheme strings as Url preserves that persisted effective ceiling's allow/deny meaning under the same scheme resolution. Example for every affected local journal: ["local://"] → [[{"url":"local://"}]]. Old [] must become **[[]]**, never [] or omitted/null. Missing/null stays unrestricted. Do not renormalize an absolute persisted root against a different cwd. This is semantically exact for the stored flattened permission set, **not reconstruction of the lost original layers**: old lexical intersections already discarded path/URL overlaps and independent ancestor constraints. A reader cannot recover those lost distinctions; adopting a one-layer ceiling cannot retroactively promise the original multi-layer invariant. Malformed/non-normalized legacy strings would need a separately specified fail-closed policy rather than guessing.

Upstream explicitly documents “Older child headers with string entries in writes are not supported” (axo/crates/axo/docs/sessions-and-compaction.md:37-41). Commit 0f4f890203cd1da30b7c43dc55080c4e42b84187 message is only “fix: enforce layered write scopes and resolve review findings”; it supplies no additional migration rationale. Its plan/design.md delta replaces flattened intersection with separate layers, typed persistence, and per-layer enforcement (current axo/plan/design.md:171); plan/plan.md records the layered inherited write-scope feature. Neither inspected plan delta establishes that conversion of valid effective old lists is impossible. The explicit [] security comment is the concrete reason to reject ambiguous zero-layer input, not evidence that the nine local:// ceilings cannot be represented.

### Options seen

1. **Accept the incompatibility** — actual axo 614089b behavior/documented contract. No migration machinery, but all nine indexed children disappear from listing, are uninspectable/unresumable, and their usage is omitted. Roots are not lost. This is a user-visible data-access regression, not merely old orphan cleanup.
2. **Axome-owned one-time conversion** — technically representable for these nine exact headers; preserve all other header fields/entries and use backups/atomic replacement with the app stopped. This is an adoption option, **not current code**, and no conversion was performed. Host then owns identifying legacy versus layered shapes, [] handling, and malformed-input policy.
3. **Ask axo for legacy reading** — shared boundary for all read/list/open/reconcile consumers (the store Header deserializer), rather than fixing Axome paths independently. Convert valid old flattened roots to one layer, [] to [[]], leave newly written format layered. Also a proposed option, **not supported today**. Full restoration of lost original layers is not possible from the persisted old list alone. Evidence does not force one ownership/product choice.

## D3 — can an engine-created custom QueuedInput reach today's Axome queue card?

### Evidence

**No, not through normal Axome/axo producers today.** Whole-repo gitignore-respecting search for HostMessage, HostDelivery, SubmittedCustom, Session::post, and .post(...) found only docs and HTTP .post calls; explicit src/src-crates/src-tauri searches also inspected CustomMessage uses. Axome's CustomMessage matches are transcript conversion/handling and test construction, not submission producers (Axome/src-crates/axome-core/src/services/axo/convert.rs:394,443,671; live.rs:626-636). Web search posts are reqwest HTTP requests (web/grounded.rs:64,193,234,378; web/providers.rs:366,540,573,620,669,763), not Session::post. Keywords/modes do not add an Axome custom-post path.

- **The custom queue producer is Session::post.** It writes Entry::Submission with custom:Some({custom_type,display}), creates matching AgentMessage::Custom, and queues according to Steer/FollowUp/Quiet (axo/crates/axo/src/session/delivery.rs:530-577). QueuedInput::find only returns metadata from an actual matching Entry::Submission (session/mod.rs:397-429).
- **Snapshot eligibility is narrower than all pending input.** LiveSnapshot::queued is agent.queued_ids() filtered through QueuedInput::find (axo/crates/axo/src/session/mod.rs:2713-2718). Do not confuse this with hooks.queued_submissions(), which additionally collects mail/quiet IDs for recovery/run bookkeeping (session/delivery.rs:141-157). Quiet host messages go to a separate quiet queue, mail to the job registry, ordinary steers/follow-ups to the agent (same file:788-803).
- **Background results are custom messages, but not custom QueuedInput.** jobs.delivery_message builds type JOB_RESULT with a delivery-<uuid> id and no corresponding Entry::Submission (axo/crates/axo/src/jobs/mod.rs:803-824). Delivery reservation supplies job results/mail/quiet messages directly (session/delivery.rs:255-269); QueuedInput::find would reject a delivery id even if it appeared among agent IDs. Job cards/results are not editable host submissions.
- **Mail is not custom.** post_mail goes through queue(SubmissionKind::Mail); submission() always records custom:None and creates an ordinary user message (axo/crates/axo/src/session/delivery.rs:589-607,622-639,808-841). It goes to the mail queue, not LiveSnapshot's steer/follow-up agent queue.
- **Mode notices are custom transcript entries, not custom submissions.** mode_notice produces Entry::CustomMessage with type mode_notice and display:false, not Entry::Submission (axo/crates/axo/src/session/modes.rs:247-313). Other engine context/catalog custom messages similarly do not satisfy QueuedInput::find's required submission shape. Keyword expansion uses ordinary submission(), still custom:None (delivery.rs:622-639,808-841).
- **Existing durable external host posts remain an exception.** If a journal already contains a pending custom host submission from another host/import/manual edit, reopening can restore it; absence of Axome producers does not prove arbitrary journals lack custom submissions. This is not an engine-generated job/mail/mode case. Custom steering/follow-up metadata would then reach snapshot. Axome currently copies only kind/parts, filters Quiet/Mail, and withdrawal returns only ChatPart[] (Axome/src-crates/axome-core/src/services/axo/convert.rs:848-864; mod.rs:1005-1018). Resubmitting such an item as a steer would destroy its custom identity/display policy; axo explicitly says use Session::post (session/mod.rs:404).

### Options seen

1. **Ordinary-only queue with explicit unsupported-custom handling** — matches current Axome producers; adapt withdrawal API mechanically for normal parts, but never silently transform custom items into ordinary user messages. A read-only/disabled edit-promote treatment for unexpected custom items is a proposed policy, not today's implementation. No need to redesign job-result/mail/mode-notice cards on the premise they enter this queue.
2. **Full custom queue contract** — axo exposes custom_type/display and requires resubmission via post. Axome would carry that metadata end-to-end and choose visibility/edit/promotion semantics deliberately; this is needed if Axome starts posting or promises interoperability with externally produced custom submissions. display:false must not accidentally become a visible user-authored message. Quiet remains outside the current LiveSnapshot queue surface.

Evidence rules out the feared *automatic internal custom-message reachability*; it does not choose how broadly Axome should support externally supplied/future host posts.
