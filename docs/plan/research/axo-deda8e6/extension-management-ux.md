# Managing agent extensions in Axome

2026-11-22 · axo `deda8e6` · Axome `48f5a03`  
**Question:** How should users discover, install, trust, enable, diagnose and remove axo extensions on the host where their sessions run?

**Separate three decisions:** “Copy this package to my host,” “enable this ID on this host,” and “allow this folder to supply executable code” are not synonyms. A copied package can be off. An enabled ID can be unavailable. A trusted folder cannot enable anything. This distinction matters more than a marketplace.

## What to borrow, and from whom

These are comparisons of documented management surfaces, not claims about everything a third-party plugin or developer console can do. “Not documented” means the linked surfaces do not establish that behavior. In particular, none of the eight management lists below establishes a per-extension resident-memory figure, a standard live dependency-install transcript, or a universal crash-disable policy. VS Code's process tools are a useful *different* surface.

## Recommendation

**Put one host-scoped Agent Extensions page under Settings → Agent.** Use the existing host caption; for project-sensitive results show `Project: <folder>` (or `No project selected`). Follow `src/lib/features/settings/dialog/SettingsDialog.svelte:119-168,217-224` and the divided multi-control rows in `views/ProjectAccessView.svelte:59-83` (both under `src/lib/features/settings/` for the latter). Use `SettingsSection` actions, `SettingRow as="div"`, labelled switches, textual status plus a dot, menu buttons, inline alerts and monospace paths. No cards, always-on status graph or second rail button. This page manages **axo execution**, not today's language/harness manifests (`src-crates/axome-protocol/src/extensions.rs:5-40`; `src-crates/axome-core/src/services/extensions.rs:279-341`). A future common entry point can link here without merging its operations or scanning the other catalog's roots.

### The three sections and their actions

1. **Extensions** — `Install…`, `Enable ID…` (supports hand-authored lists or IDs absent here). Show the union of the host's ordered enabled list, manager statuses for the selected context, store inventory and safe authored manifest discovery. Configured IDs first, **in precedence order**, then off entries by ID. Each row: canonical ID, source (`Installed`, `User Folder`, `Project Folder` with path on expand), enabled-on-host switch, effective state and relevant action. Filters `All / Enabled / Off / Needs Attention` do not reorder enabled entries. Do not make identical plain IDs independently switchable: one configured ID, detail lists winning and ignored paths. A checkout can be unavailable *here* while working in another project. Do not overwhelm every unrelated project with failure toasts for that case. Empty state explains `Install…` vs placing an authored folder; show/copy actual host roots. Expanded detail shows manifest contributions as descriptions, **not** a permission grant or an exhaustive account of what code can do.
2. **Project Access** — show current folder, Restricted/Trusted (including inherited trust), whether the project root participates, and link to shared **Manage Workspace Trust**. No project-level enable switch. Distinguish “folder not trusted” from “ID not enabled” and from “no package in this context.” Read only inert, bounded directory/manifest metadata to present candidates on explicit review; no executable scan, dependency resolution or imports. If read would follow a link outside the folder, don't preview it as project-owned code. A banner link to review remains usable after dismissal; a restricted folder still opens and user/installed extensions remain available according to the host list.
3. **Runners** — expandable inspection by execution context, one row per live runner or group; list members, sampled PSS in MiB, and reason/generation where applicable. Label **Runner memory (PSS)**, never “memory used by this extension” for grouped members. Omitted sample means *unavailable*, not zero; Cold has no running process. Sample only while this section is visible; stop on close/host change. No memory polling in chat, duplicated totals or per-member arithmetic (`crates/axo-extensions/src/lib.rs:182-191,529-564`).

| Row state | User-facing meaning and action |
|---|---|
| Not listed in user setting | **Off**; enable on this host. Code/data stay put. Not axo's `Disabled`. |
| `Cold` / `Ready` | **On demand** (normal; starts on use) / **Ready**. No Start button. `Reload Code` for code edits. |
| `Installing` / `Starting` / `Restarting` | **Installing Dependencies / Starting / Restarting**, with spinner and latest reason. Suppress duplicate actions while in flight; no repeating toast for the automatic restart sequence. Track host fetch/store-install progress separately: first-time installed-but-off packages have no manager phase. |
| `Disabled` | **Stopped after failure** (still enabled in settings); show actual reason, `Retry` or disable explicitly. Explain when a group shared the crash budget rather than blaming every member. |
| `Unavailable` | **Unavailable** with reason/path/context. Offer the applicable fix: enable trust via Manage, install missing package/dependencies, correct input, provision packaged Bun on the *host*, or `Retry`. A host-imposed trust block is Axome state, not a fabricated manager phase. Keep unclassified upstream reasons as text, not brittle parsed enums. |

**Ordering, grouping and conflicts.** Move Earlier/Later on enabled rows (keyboard-accessible; show later-ID-wins for provider declarations). Advanced row detail: **Runner Group**, default `Separate runner`; typed valid name or select existing, `Clear Group`. Explain shared process, memory, restart and in-flight interruption; list affected IDs before an operation that recycles a live placement. A group is not a trust sandbox. Provider conflict detail should read e.g. `Provider acme → lab/model-tools; hides host provider acme`, with links to both extension and Providers where applicable. An unavailable winner is still the winner; do not silently use the hidden credential or suggest deleting it. Authored root collision is **different**: first matching root wins even if broken; do not offer list reordering to fix two copies of the same ID. For slash commands, tools, definitions etc., show actual session diagnostics; do not invent a universal precedence rule. See `crates/axo-extensions/src/{lib.rs:113-180,388-445,manifest.rs:203-247,session.rs:66-105,265-318}`, `crates/axo-ai/src/models/mod.rs:516-539,659-689`.

### Authority, persistence and trust

- The source of enablement is the **owning host's user settings only**: e.g. `~/.config/axome/settings.jsonc` → `{"axo":{"extensions":[{"id":"notes"},{"id":"lab/model-tools","group":"lab"}]}}`. No shadow enablement table. Extend protocol `AxoSettings`, its default, schema and typed DTO with the ordered list; preserve unknown-field rejection and validate IDs, uniqueness and group using axo's grammar. `Enable ID`, ordering, group editing and removal cover the full setting without requiring an editor. Do not accept project/user-effective merged JSON as authorization; a project `axo.extensions` produces an ignored/user-only diagnostic, never code execution. Evidence: `src-crates/axome-protocol/src/axo_settings.rs:9-44`, `src-crates/axome-core/src/services/axo/config.rs:21-85`, `crates/axo/src/config.rs:73-160,659-676`.
- Have the core service edit the latest array by ID under `SettingsService::update_section` (section patch/atomic file replacement, `src-crates/axome-core/src/services/settings.rs:26-34,72-116`). No debounced whole-array replacement from stale frontend drafts. Same validation/reconciliation for UI saves and external file edits; invalid input leaves last good runtime and shows the file error. Once a valid setting is saved, configure each affected live context; report a runtime failure separately from the durable intent. Cache no enabled flag on the client. Scope reads, mutations and events to captured host and, where applicable, folder; a remote browser's path is not a server filesystem path.
- **D4 is the trust prompt.** Unfamiliar folder opens restricted, dismissible top banner `Trust Folder` / `Manage`, persistent badge, no blocking launch modal (`docs/plan/design.md:39`; current bypass `src-crates/axome-core/src/services/axo/mod.rs:439`; `TODO.md:10`). In the shared trust details add: “Enabled agent extensions in this folder can run code as your account, install dependencies, access files and create or close sessions.” Show folder, host, discovered IDs if known, which are enabled and what their source would be, *before* approving. Trust is the existing host-stored decision with parent/worktree inheritance, not a repo file, extension allowlist, or second prompt on each branch. It trusts future contents of that folder too. Enabling a plain ID is host-wide: label that it may resolve to different code in another **trusted** folder. No untrusted root, provider registration, static contribution, dependency install, or lazy callback from project packages before consent. Keep authored dependency installation explicit (`auto_install=false`; button only for admitted enabled authored code).
- Preserve the actual folder boundary **at runtime**. Adding a trusted folder must not add its authored root to a host-wide manager serving other projects: options/roots are fixed and providers publish into the supplied engine (`crates/axo-extensions/src/lib.rs:76-110,362-400`). Use isolated folder resolution/provider contexts; global Settings can manage store and list without adopting a current tab's roots. Revocation/inheritance changes must recompose affected sessions and retire project-origin runners and provider layers before reporting the restricted state as applied; do not merely hide a row or defer revocation until restart. Trust does not undo past code execution. For new root sessions created by extensions, resolve destination folder and its own trust context via the normal host lifecycle, never inherit caller trust or treat a background lifecycle request as interactive consent. Trust in A cannot authorize B. Manage storage/updates on the owner host; after an update/revert/uninstall, all affected contexts reconcile, not just the manager through which the store call was made.

### Acquisition and removal

**Offer two sources: host folder and Git URL.** `Install…` opens a source selector. For a host folder browse on the execution host (or enter a host path); distinguish copying an installed `publisher/name` package from a plain-ID **authored** package run in place from an authored root. For the latter show its actual expected location and `Enable on Host`, not `Install`/`Uninstall`. For Git take repository URL and optional ref, resolve to an exact commit on that host, stage privately, and inspect the manifest without running it. Show resolved ID/SDK, origin/path, commit, declared contributions and target host. Explicit `Install Package` confirms that dependency scripts may run **now**, even if activation is off. Never default to enabling on install; success presents `Enable on Host`. Do not build a discovery registry, accept npm specs or silently treat a package.json as an axo manifest. npm distribution conventions do not guarantee axo's installed ID, SDK or frozen Bun lock. An author can distribute via Git or a ready package folder without depending on registry conventions. Use host Git transport with explicit supported schemes and argument handling, not shell snippets; no hook/submodule/script execution as part of source preview. Do not store credentials in displayed origins.

**No automatic upgrades.** `Update from Source` reacquires the recorded host folder/ref, resolves the prospective revision, shows old/new when known and affected live runner members, and uses the same review/install operation. A full Git SHA is a fixed pin; branch/tag are locators, the installed snapshot never changes until approved. `Choose Revision…` supports a new pin without requiring raw settings edits. Canonical origin identifies the repository (and package directory if supported), *not* a moving commit, ref, or temp checkout. Persist the requested ref and resolved revision per installed copy as host acquisition metadata, separately from enablement; tie it to axo's published copy, not merely to last attempted install. If history is unknown show “previous installed copy”, not a fabricated version. Origin changes require a separate `Replace Source` confirmation comparing old and new source; default `replace_origin=false`. `Roll Back` only for `has_previous`; state explicitly it swaps two copies and the same operation can return to the other one, not an unrestricted version history. After source replacement and rollback distinguish **update source** from **running copy provenance**: axo retains the record's origin when swapping versions. `store.rs:319-332,390-400,428-452,468-486` also shows why a post-publication reload failure must be reported as “installed, reload failed” after reading current state, not “nothing changed.”

**Disable ≠ uninstall ≠ erase.** `Disable on Host` removes the ID from the user list; never deletes files. `Uninstall…` only for managed packages: identify host, current/previous copies and affected contexts; if enabled, confirm `Disable and Uninstall`, save and reconcile all contexts first, then call `uninstall(id, delete_data)`. If deletion fails after disable, show **Off, still installed** and allow retry. Default `Delete extension data` unchecked; show the exact managed data directory and warn deletion is irreversible. External files, settings the package wrote elsewhere, provider accounts/credentials and authored source trees are not included. Never rm an authored checkout; `Open Folder`/copy host path and disable suffice. Upstream operations and limits: `crates/axo-extensions/src/lib.rs:448-527`, `store.rs:91-108,335-381,408-432`; lifecycle scripts are unsandboxed (`deps.rs:87-105`, `process.rs:109-118`).

### Diagnostics belong where the user can act

- Have `axome-core` own an agent-extension management service, host-side source acquisition, store commands, D4 admission and snapshots; expose typed host/folder operations/events via `axome-protocol` to both Tauri and server. Svelte owns presentation only. Subscribe before snapshot; reconcile after reconnect/lag. Join settings/store/discovery with statuses; `status()` is **enabled only**. Distinguish host install operations, manager events and session-specific notices. An interrupted update is not a successful reload. Provide enough source context on unavailable provider notices to distinguish an extension failure from expired credentials. If path-based provider identity changed after update, point to Providers to sign in again; never copy credentials between slots (`crates/axo-ai/src/models/mod.rs:294-324`; `crates/axo-extensions/src/lib.rs:1152-1164,1293-1300`).
- **Row detail:** latest reason, diagnostics, provider winners/hidden origins, session link where known and copyable install error/output. Show the actual bounded failure tail as plain text and label it **Install output (tail)**. Retain bounded host operation results for reconnect/reopen; redact credentials and never replay raw output into chat. Do not advertise live Bun stdout, a complete install log, or console inspection: manager emits diagnostics and phases, runner output is drained, failure capture is bounded (`crates/axo-extensions/src/process.rs:98-150`, `deps.rs:23-30,134-145`, `lib.rs:113-180,403-420`). A cancelled viewer is not proof a host operation stopped.
- **Outside Settings:** user-invoked install/update failure gets one notification with `View Details`; background crash-budget exhaustion or new material conflict gets one deduplicated host/context notice, not one toast per generation. Keep expected cold/off/transient phases out of Notifications. Use existing notification tone/history (`src/lib/features/notifications/state.svelte.ts:6,93-101`). Failed tool/command/provider stays at the affected invocation; new `SessionDiagnostic` appears as an unobtrusive system notice in that session's UI, not an assistant message or model prompt. Link Settings filtered to the owning host/context/ID when known. Preserve sessions whose unrelated contributor failed; do not bypass a failed policy or automatically replay interrupted calls. No permanent extensions status-bar meter: D4's persistent restricted badge already owns the global trust signal.

**Alternatives rejected**

- A marketplace-first sidebar: there is no axo registry to browse, and an install source is not an endorsement.
- Per-project enable lists or per-session switch: contradicts upstream's user-only setting; trust gates code sources, not the user's intent.
- A modal for every project extension, or inheriting the current unconditional project trust: fragments D4 or permits silent code execution.
- Group names editable only in JSON; memory on each package row: the former violates complete UI coverage, the latter double-counts shared runners.
- Automatic update/enable or uninstall-as-purge: executes new code or deletes user data without a distinct decision.

## Needs Toph

None. The host-scoped controls, source review and existing Workspace Trust decision cover full extension support without an additional product-policy choice.
