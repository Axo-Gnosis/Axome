# Two extension systems: give the workbench adapters their own name

2026-11-22 · axo `deda8e6` · Axome `48f5a03` · Q72: Where do Axome’s existing extensions clash with axo’s Bun extensions, and what should change?

**Call the existing system “Axome integrations.” Reserve “extensions” for axo packages.** Installing the Codex terminal CLI makes **New Session → Codex** available; enabling an axo model provider affects **Models / Providers** in native chat. Neither operation should imply the other. The boundary is *which API the package extends*, not whether the package contains executable code. Preserve this distinction from the folder on disk through to the error shown to the user.

## What must survive the rename

**“Installed” has three meanings.** (1) Put an Axome integration folder on the selected host and reload, or use a bundled definition. (2) Supply its *external tools* on that host. `dev.axome.vtsls/extension.json:31–51` names `vtsls` and gives package-manager guidance; `dev.axome.codex/extension.json:7–22` names `codex`, its probe target, history and resume behavior (both under `src-crates/axome-core/extensions/`). `requires` is a PATH check, not a resolver of package IDs. A contribution’s hint overrides its package hint. Bare commands resolve in the effective environment; disk packages can ship `./` executables; overrides can select another binary. Harness availability runs a version probe; LSP status resolves the command, not a successful LSP handshake. Users supply executables via their environment, folder Nix shell or configured paths; Axome does not execute `install_hint`. The declarative manifest is not a sandbox: e.g. a history helper can run when history is listed. `service:544–574,720–777,900–931`; `src-crates/axome-core/src/services/{harnesses.rs:17–35,77–94,179–240,lsp.rs:591–650}`; `src-crates/axome-core/src/operations/formatting.rs:59–88`. (3) An axo **managed install** copies a host-local axo source folder into a versioned store and may execute Bun dependency scripts; installation does not enable the extension (`axo:crates/axo-extensions/src/lib.rs:448–527`, `deps.rs:87–105`). Never offer “Install Dependencies” as a fix for a missing terminal CLI.

## Where the collision becomes observable

| If we reused … | What would break |
|---|---|
| `extension.json` or one scanning root | Axome expects `label/version/api/contributes`; axo requires `id/entry`, plus `sdk` for managed installs, with top-level declarations. Both reject unknown fields (`protocol:12–40`; `axo:crates/axo-extensions/src/manifest.rs:149–175,250–279`). A Bun package in the current Axome drop-in root yields an invalid-folder diagnostic; it is not activated. A workbench manifest in an axo authored root does nothing unless its ID is enabled; then it claims the first matching slot, fails validation and makes that extension unavailable **even if a valid lower-priority root exists** (`manifest.rs:203–247`; `axo:crates/axo-extensions/src/lib.rs:113–142`; `service:393–449`). A union JSON object fails both validators. A single folder cannot provide two different root files with that name. Do not try both parsers and pick the one that succeeds. |
| A common install store | Current Axome scans *every* ordinary child as a package. An axo `<store>/<publisher>/<name>/install.json` record selects the current version directory, not a manifest in `<store>/<publisher>`. Feeding that store to Axome emits missing-manifest diagnostics; copying an Axome drop-in there creates no axo install record. Neither store layout is the writable per-extension data root or ephemeral runtime socket directory (`service:375–430`; `axo:crates/axo-extensions/src/manifest.rs:210–220`, `store.rs:25–45`, `lib.rs:76–110,1303–1323`). Never scan a parent containing both systems, never put authored package roots under a managed store, never remove the other system’s files on uninstall. |
| Shared identity, status or cache | `dev.axome.codex` is a valid Axome package ID **and** syntactically a plain authored axo ID; axo installed IDs use `publisher/name`, and enabled order/group has runtime meaning (`axo:crates/axo/src/config.rs:73–160`). Equal text need not denote the same author, package or credential owner. `codex` the terminal harness can coexist with a model provider named `codex`. A missing binary or invalid catalog entry is not axo `Disabled`/`Unavailable` or a shadowed model provider. Axo’s own `ExtensionDiagnostic {id,message}` is not Axome’s path-bearing diagnostic (`axo:crates/axo-extensions/src/lib.rs:113–180`; `protocol:316–342`). Never reference either by a shared untyped bare ID. Do not key project-sensitive extension placements by the old host-only integration cache. |
| “Enable”, “reload”, or `extensions` settings | An auto-discovered host integration can be usable for highlighting while an individual binary is missing/disabled. Axo’s ordered `{id,group?}` list is user-only, even for **trusted** project packages (`axo:crates/axo/src/config.rs:47–51,73–160,659–676`). Axome feeds the `axo` subtree to the harness (`src-crates/axome-core/src/services/axo/config.rs:21–85`); its own strict settings model must gain `axo.extensions`, **not** top-level `extensions`. A package’s files being present permits neither project self-enablement nor automatic dependency execution. Axo reload targets one placement and may interrupt grouped peers; **Reload Integrations** must never call it. |
| One ambiguous UI/docs term | A user following “put it under extensions and reload” might be trying to repair a grammar, launch a terminal agent or run trusted Bun code with native session access. A provider contribution belongs in native chat, not the terminal New Session picker. Diagnostics, palette verbs, Settings host captions, package paths and authors’ examples must name the subsystem, especially when the host is remote. Use explicit provenance where the context does not supply it: **Integration: …** vs **Extension: …**. |

## Four possible designs

| Option | Work and compatibility | User result / assessment |
|---|---|---|
| **A. Rename Axome’s system end to end** | Mechanical but cross-stack: files, compiled includes, diagnostics, protocol, TS, paths, docs and palette IDs; no upstream change, runtime redesign or migration. | “Integrations” covers both workbench languages and terminal CLIs. “Language packs” excludes the latter (and means localization in VS Code); “plugins” is just another word for executable extensions. Distinct filenames make errors actionable. **Pick A.** |
| **B. Rename only axo’s user-facing label**, e.g. “Agent Add-ons” | Lowest UI churn, but still need disjoint roots, install paths, code/protocol names and explicit target for reload. axo keeps strict `extension.json`, its SDK and `extensions` key. Changing those upstream is more than a label and affects every host. | Settings, author docs, source folder and error messages would use different words for the same object; a copied manifest remains indistinguishable by filename. |
| **C. One Axome package + one Extensions page** | Feasible as an Axome-owned envelope (`axome-package.json` plus separate workbench and native axo subdirectories/manifests). Axome validates and routes each part, admits raw axo packages too, maps installed and authored identities, and coordinates activation, update, rollback, removal, partial failures and per-part scope. One page must still distinguish package installation, binary availability, trusted code enablement and folder/host ownership. | Good if authors regularly ship both parts as a unit; an editor integration must still work without Bun. Don’t add LSP/Monaco/harness fields to axo or relax its strict parser. A versioned **host-neutral** optional metadata/sidecar convention could support multiple hosts if actually needed; it does not solve atomic install or authorization. One-page organization alone does not require a new package format. |
| **D. Keep both “extensions”, separate directories and UI sections** | Lower churn than A: scope all paths, command labels, messages and docs as “Workbench Extensions” vs “Agent Extensions”; separate protocol namespaces anyway; both keep `extension.json` and their own parser, no upstream change. | Works technically but every support exchange, source checkout and copy/paste example needs the qualifier. The most useful distinction disappears outside the UI. |

### What VS Code and Zed actually demonstrate

[VS Code’s manifest](https://code.visualstudio.com/api/references/extension-manifest#combining-extension-contributions) combines declarations such as languages, grammars and snippets in **one** `package.json`, with optional activation/code, one extension identity and multiple discovery categories. Its [LSP architecture](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide#overview) explicitly puts a **normal extension** on the client side and a separate language-server executable on the other. One UI is natural when the editor defines the common extension API; it does not make server binaries equivalent to packages.

[Zed’s author guide](https://zed.dev/docs/extensions/developing-extensions) likewise uses **one** `extension.toml` for languages, themes and other contributions; categories are derived from features, and procedural parts can use Wasm. Zed historically included [Assistant slash commands in that same manifest](https://github.com/zed-industries/zed/blob/11efe82a1fa35f4c6b66a88e8c0c9fc5f5cb67a6/docs/src/extensions/slash-commands.md), not a separate package type; the legacy Text Threads/slash-command crates were [removed in March 2026](https://github.com/zed-industries/zed/commit/76c6004b27e15531785ce83919dbd7ae96f05ec5). The precedent supports C *when one platform owns publication and activation*. Axome owns the workbench; axo already supplies a portable package, lifecycle and management contract independent of it. Borrow the clear contribution labels, not an extra envelope.

## Recommendation

1. **Cut over the workbench contract first.** Rename the repository folder to `src-crates/axome-core/integrations/`, the compiled and drop-in manifest to `integration.json`, and the host root to `dirs.data/integrations/<id>/`. Keep API 1 semantics, bundled IDs, contribution IDs, composite ID strings and existing settings keys. Rename `extensions` modules to `integrations`, `ExtensionService`/`ExtensionCatalog`/`ExtensionDiagnostic`/`ExtensionGrammar` and their runtime/settings/loaded counterparts to `Integration…`, provenance fields to `integration_id`/`integration_label`, including LSP/formatter/harness status or descriptors where applicable. Move `features/extensions` to `features/integrations`; use `backend.integrations` and `integrations_get_catalog/get_grammars/reload` (all three with the `integrations_` prefix). Change both transports from the single RPC table, commands, bindings, cached calls and affected fixtures together. Not a global replacement: leave file suffix arrays, WebGL/xterm APIs, OMP’s own extension locations and axo terminology alone.
2. **Give axo its own address space.** `axo-extensions` owns strict `extension.json`, package IDs, store records, runner generations and data deletion. Axome core supplies distinct host/user-authored and D4-trusted project roots, managed store, persistent data and runtime directories — none equal to, above or inside `dirs.data/integrations`. Reserve e.g. `dirs.config/extensions/<id>/extension.json` and `<trusted-project>/.axome/extensions/<id>/extension.json` for authored axo code; give the managed store and runner data separate axo-owned subtrees of `dirs.data/axo`. Keep `dirs.data/extensions` **unclaimed**, not a fallback or a Bun scan root. Do not copy or auto-convert old user files. If an author ships both, use two independently loadable source directories, not a hybrid manifest. Distinguish the paths of wrong-format packages in diagnostics; never activate an alternative loader as recovery.
3. **Route actions by meaning.** Keep **Languages** and **Workspace → Harnesses**; use **Reload Integrations** (`reload-integrations`), “Integration not loaded” and matching help/hints. Do not add a duplicate directory browser/marketplace page for drop-ins. Add host-captioned **Agent → Extensions** for axo; a palette search for extensions should find that page, not rerun all editor integrations. Use existing `SettingsSection`/`SettingRow` lists, not a parallel settings shell. This page owns full enablement, order and group editing, authored/installed/project distinction and runner/package management, with separate axo-specific DTOs/RPC. Preserve Provider credential controls in **Providers**, CLI controls in **Harnesses**. Make explicit in the README which file to author, where it lives on the target host and whether the user must reload, enable or supply a binary; rename the history guide and bundled links with their directory. Never suggest that installing the grammar authorizes running an axo package.
4. **Do not share enablement or trust.** Add typed `axo.extensions` to the host settings mirror and `/axo/extensions` to the folder-pruned global-only pointers; expose its entire list through Settings (D4, `docs/plan/design.md:39`). A project can supply code, not its own allowlist. Use D4’s host-stored folder trust with parent/worktree inheritance: Restricted Mode does not admit the project root; trust makes it eligible, not enabled. This is *designed, not present* (`TODO.md:10`); implement the trust gate with project extension support, not a second trust system or the current unconditional session trust. Project placement must not replace another folder’s globals or providers. New extension operations execute on the owning host; do not reuse integration reload, diagnostics, install hints or cache entries for them. No axo schema change required.

**Acceptance cases for the cutover:** a bundled grammar and a same-spelled enabled axo package coexist; either can reload without touching the other; a rejected override leaves its bundled integration usable; the old drop-in root is inert; a restricted or merely unopened project cannot publish host providers; a remote-host package operation never reads a desktop-local package by accident. These are planning criteria, not test results.

**Rejected alternatives:** B — label-only leaves author and runtime vocabulary split. C — two independent activation/rollback/trust contracts make a unified installer misleading without real demand for joint releases. D — disjoint paths work, but two packages still answer to the same filename and everyday name.

## Needs Toph

None. The naming and layout recommendation requires no change to the agreed scope, trust model or migration policy.
