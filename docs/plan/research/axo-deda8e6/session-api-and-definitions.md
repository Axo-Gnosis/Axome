- Axome HEAD: `48f5a03`.

- Question: What changed in axo's Rust host-facing session/construction API, and which existing Axome surfaces consume those contracts?

This is a source inventory, not an adoption design. `axo:` paths are relative to `/repo/rust/axo` at the target; `Axome:` paths are relative to Axome HEAD. ## 1. Definitions and construction

| Base API | Target API | Axome consumer |
|---|---|---|
| `SessionOptions::{agents,modes,keywords}` | `SessionOptions::definitions: Definitions` | Chat construction: `src-crates/axome-core/src/services/axo/mod.rs:431-448`; memory capture: `src-crates/axome-core/src/services/memory/writer.rs:248-257`; direct-session fixture: `src-crates/axome-core/src/services/axo/tests.rs:863` |
| `Axo::catalog(cwd, access, agents, modes, keywords)` | `Axo::catalog(cwd, access, &Definitions)` | `src-crates/axome-core/src/services/axo/bundled.rs:76-83` |

Sources: axo `crates/axo/src/session/mod.rs:96-137,2553-2563,2665-2677,3044-3088`; `crates/axo/src/axo.rs:410-419`.

`Definitions` is a cloneable/default/partial-equality Rust struct with `agents: Vec<AgentSpec>`, `teams: Vec<TeamSpec>`, `modes: Vec<ModeSpec>`, `keywords: Vec<KeywordSpec>`, and `skills: Vec<Skill>` (`axo:crates/axo/src/context/definitions.rs:12-20`). Thus host-bundled personas, modes, and keywords remain parsed specs, now grouped in one object; code-supplied teams and skill descriptors also have first-class slots. This does not turn a `Skill` into an inline-body definition: rendering still reads its `path` (`axo:crates/axo/src/session/prompt.rs:628-641`). Axome bundles `scout`, `task`, the separate `memory-writer`, `orchestrate`, and four modes; it substitutes the configured plans directory into mode bodies before session construction (`Axome:src-crates/axome-core/src/services/axo/bundled.rs:20-60,85-95`).

### Precedence and liveness

- Files are discovered once at session startup; `FileDefinitions` explicitly retains that immutable input. Merge precedence is **file definitions, then layer definitions, then host definitions**, first matching name wins. Agents and teams enter one agent-definition list; skills/modes/keywords merge by their respective loaders (`axo:crates/axo/src/context/definitions.rs:22-29,63-86,101-128`; `crates/axo/src/session/prompt.rs:435-479`). This is distinct from the last-registration-wins rules for commands and ordinary registration lists.
- `set_definitions` replaces only host code definitions. It merges against original files plus the current layer; compares resolved values; rebuilds spawn/enter-mode tools and the prompt when changed; returns merge/skill/command/tool diagnostics. It does **not** reload definition files, persist the host registration object, or mutate the selected persona/mode copy. Hosts supply code definitions again on reopen (`axo:crates/axo/src/session/mod.rs:3044-3088`; `crates/axo/src/session/prompt.rs:435-479`).
- Current `agents`, `skills`, `modes`, `keywords`, and `commands` reads reflect the new merged catalog. Spawn resolution and keyword matching use live definitions; the `skill://` resolver shares `LiveDefinitions`. An existing selected persona/mode retains the spec selected earlier, even if its name is removed or replaced in the catalog (`axo:crates/axo/src/context/definitions.rs:41-59`; `crates/axo/src/session/mod.rs:2553-2563,2636-2642,3044-3048`; `crates/axo/src/session/spawn.rs:340-342`; `crates/axo/src/session/delivery.rs:249-253`; `crates/axo/src/session/modes.rs:49-77`).
- There is **no definitions/catalog-changed session event**. The setter returns diagnostics, and `diagnostics()` remains start-time diagnostics. `SessionEventKind` enumerates activity, entry, queue, questions, jobs, context, mode/result and usage—not catalog changes (`axo:crates/axo/src/session/mod.rs:327-377,2565-2569,3044-3138`). Axome captures command/toolbox catalogs when it creates `LiveSession` (`Axome:src-crates/axome-core/src/services/axo/live.rs:850-864`). Open point: a live catalog can now change independently of the snapshot Axome currently publishes; axo does not supply a dedicated catalog notification.
- `keywords_enabled: false` sets file-keyword input to `None`; the merger then excludes **all** keyword sources, including later host/layer registrations. This remains stronger than disabling individual keyword names. Axome's memory writer already sets it false for non-user-authored capture prompts (`axo:crates/axo/src/context/definitions.rs:27-28,72-76,113-116`; `Axome:src-crates/axome-core/src/services/memory/writer.rs:250-253`).
- Public file loaders now take only roots: `load_agents(roots)`, `load_modes(roots)`, `load_keywords(roots)`; they no longer accept code fallback lists. No direct Axome consumers of these loaders were found; Axome uses `Axo::catalog` and spec parsing (`axo:crates/axo/src/context/agents.rs:240`; `context/modes.rs:126`; `context/keywords.rs:74`; `Axome:src-crates/axome-core/src/services/axo/bundled.rs:4-17,82`).

## 2. Host/layer registrations and inheritance

`Registrations` contains definitions and six lists: tools, tool policies, spawn hooks, schemes, sections, commands. `SessionOptions::layer` is a second registration set; host fields remain separate. Ordinary lists join **host then layer**, while definition merging explicitly reverses those two sources for first-name-wins (`axo:crates/axo/src/session/mod.rs:125-136,164-191`; `crates/axo/src/session/prompt.rs:435-442`). Layer schemes and commands can replace a same-name host entry; tool conflicts are shaped/diagnosed by the tool merger. This is not a replacement of Axome's host contributions with an extension-only session.

| Live method | Target semantics |
|---|---|
| `set_layer(Registrations)` | Replaces the entire layer, checks sections and schemes before committing; invalid section or reserved/invalid scheme rejects without changing the layer; stages definitions, hooks, commands, sections and tool shape, then rebuilds prompt; returns diagnostics |
| `set_sections(Vec<(String, Option<String>)>)` | Replaces host section set; invalid name rejects whole set |
| `set_section(name, body)` | Edits host side only; joined layer still applies afterward |
| `set_tools(Vec<HostTool>)` | Replaces host factories, still honors persona allowlist; return changed from `Result<(), Error>` to `Result<Vec<Diagnostic>, Error>` |
| `set_tool_policies(...)` | Replaces host policies for later hook passes; existing children retain theirs |
| `set_spawn_hooks(...)` | Replaces host hooks for subsequent spawn resolutions |
| `set_schemes(...)` | Immediate URL-registry replacement; prompt docs from next request; validates whole set |
| `set_commands(...)` | Replaces host commands; returns diagnostics including layer registrations and hidden skills |

Sources: `axo:crates/axo/src/session/mod.rs:2644-2663,2921-3138`; policy installation: `crates/axo/src/session/policy.rs:247-285`. These host mutators reject children. The JSON dispatcher withholds them: extensions register through their manifest rather than replacing the host's lists. There is no current Axome caller of these new mutators or a custom `ToolPolicy`/`SpawnHook` implementation in the surveyed code. Current chat construction passes an empty section list, web/browser/memory tools, custom schemes, and default hook lists (`Axome:src-crates/axome-core/src/services/axo/mod.rs:422-459`); the browser's policy module explicitly describes ToolPolicy as future work (`src-crates/axome-browser/src/policy.rs:7`).

Forks clone the host/layer split as it exists at fork time; host commands travel with that split (`axo:crates/axo/src/session/mod.rs:3401-3414`). Children get a **joined snapshot** of sections, tool factories, schemes, policies, and spawn hooks. Their agent and skill catalogs are captured in `FileDefinitions`; modes/keywords and registered commands are absent. Live updates to a parent do not rewrite an existing child; revival uses its seed registration snapshot (`axo:crates/axo/src/session/spawn.rs:210-254`; `crates/axo/src/session/children.rs:331-342`). Axome already reaches child sessions through `engine.axo.session(id)` (`Axome:src-crates/axome-core/src/services/axo/mod.rs:542`).

## 3. Registered commands and composer contract

Rust hosts can register commands themselves. `RegisteredCommand` holds name, description, argument hint, optional origin label and `Arc<dyn CommandHandler>`; the async handler receives `&Session` and the trimmed remainder of the input line. Registration is through `SessionOptions::commands`, a layer, or `Session::set_commands` (`axo:crates/axo/src/commands.rs:54-78`; `crates/axo/src/session/mod.rs:128-136,2644-2663`).

Catalog ordering is built-ins → modes → effective registered commands → skills not hidden by those names. Names must be nonempty and contain neither whitespace nor `/`; built-ins and modes reserve their names. Last registration of a duplicate wins, retaining the first occurrence's catalog position. Diagnostics identify invalid/hidden/replaced registrations and hidden skills. Registered commands always advertise `CommandPolicy::Alongside`; there is no configurable policy field on `RegisteredCommand` (`axo:crates/axo/src/commands.rs:402-550`).

`Session::parse_command` resolves built-ins, modes, then registered commands, returning `Command::Registered { name, args }`; unknown slash words remain ordinary/skill input. `Session::run_command` resolves the current winning handler and awaits it, or returns `InvalidCommand` if unavailable. In contrast, static `Command::decode` and `Command::parse` remain **built-in only** (`axo:crates/axo/src/session/mod.rs:2693-2752`; `crates/axo/src/commands.rs:376-399`).

Axome's command conversion exhaustively handles only builtin/skill/mode, and its serialized `ChatCommandKind` has those same three cases. Its named-command service calls static `Command::decode`, not the live session parser. The composer has separate schema-driven built-in and mode paths (`Axome:src-crates/axome-core/src/services/axo/convert.rs:84-98`; `src-crates/axome-protocol/src/chat.rs:591-614`; `src-crates/axome-core/src/services/axo/mod.rs:1601-1621`; `src/lib/features/chat/elements/prompt-input/PromptInputRoot.svelte:309-339`). These are both a Rust enum compatibility boundary and an unrepresented new command capability, not automatic extension-command UI support.

`CommandPolicy` serialization changed to camelCase: `WhenIdle` becomes `whenIdle`. Its Rust variants are unchanged. Axome explicitly converts to its own enum, whose serde spelling remains snake_case (`when_idle`), and the composer checks that spelling. Consequently axo's wire rename does not itself change Axome's current frontend protocol (`axo:crates/axo/src/commands.rs:80-90`; `Axome:src-crates/axome-core/src/services/axo/convert.rs:88-92`; `src-crates/axome-protocol/src/chat.rs:579-588`; `src/lib/features/chat/elements/prompt-input/PromptInputRoot.svelte:314,328`). `/tier` is an additional built-in and `Command::Tier` an additional variant; tier semantics are inventoried separately (`axo:crates/axo/src/commands.rs:46-48`).

## 4. Host/lifecycle and wire seams

### Native host and dispatch are distinct

`axo::ext` is new public API. `Caller { namespace: Option<String> }` accompanies positional-JSON dispatch. `Axo::invoke(object, method, args, caller)` accepts `host`/`models`; `Session::invoke(method, args, caller)` dispatches session methods. `ext::objects()` publishes callable and withheld method metadata for `session`, `tools`, `host`, `models`, and `types`. These are Rust-facing entry points too, not mandatory replacements for typed native methods (`axo:crates/axo/src/ext.rs:13-47,82-93,273-328`; `crates/axo/src/axo.rs:204-218`). No current Axome consumer of this dispatcher was found.

The new `host.rs` contains a private wire adapter, **not a replacement Rust lifecycle trait**. It exposes paged session reads, base64 snapshot reads, a file-only catalog, syntax validators, parsers for commands/specs, journal projection/job reconstruction, change squashing, project roots, and skill argument helpers (`axo:crates/axo/src/host.rs:24-200`). Its wire catalog deliberately supplies empty programmatic definitions, unlike native `Axo::catalog`. Axome's bundled catalog uses the native method, so those two catalog entry points do not describe identical inventories.

The lifecycle trait resides in `axo-extensions::Lifecycle`: `create`, `open`, `fork`, and `close` each receive `&Caller`. The host must construct sessions through its normal options path, retain them and update its UI; the extension manager's lifecycle binding runs operations to completion even if the requester disappears. Native `Axo::{create_session,open_session}`, `Session::fork`, and `shutdown` remain ownership operations withheld from ordinary JSON dispatch (`axo:crates/axo-extensions/src/lifecycle.rs:37-74`; `crates/axo/src/axo.rs:227-265`; `crates/axo/src/session/mod.rs:2800-2804,3272-3276`). No current Axome lifecycle-trait implementation; existing construction/ownership remains in `Axome:src-crates/axome-core/src/services/axo/mod.rs:412-449` and `live.rs:845-885`. Caller identity is supplied to the host; it is not itself a host authorization decision.

Wire `post`, `appendCustom`, and `custom` prefix custom types with `<namespace>:` when a caller has one; empty types fail. Typed native operations keep their explicit caller-provided custom type (`axo:crates/axo/src/session/wire.rs:52-92`; `crates/axo/src/session/mod.rs:2511-2550`). Wire spawn/team calls return receipts, not owned child handles; parse-command flattens nested results; bytes cross as base64 (`crates/axo/src/session/wire.rs:94-116`; `crates/axo/src/ext.rs:171-174`). No current Axome wire consumer.

### Session paging, snapshots, subscriptions

- `SessionStore::read_page(path, after, limit)` is a defaulted trait addition. Default implementation reads the whole journal then slices; `JsonlStore` overrides it with streaming reads and file-stamp/offset checkpoints. The wrapper returns header, entries and `more`, defaulting to 256 entries and clamping to 1–1024. Existing `Axo::open_session_read` remains a whole-journal read (`axo:crates/axo/src/store/mod.rs:27-43,85-99`; `crates/axo/src/store/jsonl.rs:252-318`; `crates/axo/src/host.rs:15-53`; `crates/axo/src/axo.rs:337-340`). Axome uses `JsonlStore` but its native history/memory readers still call `open_session_read`, so wire pagination does not automatically bound them (`Axome:src-crates/axome-core/src/services/axo/engine.rs:78`; `services/axo/mod.rs:1519,1732,1942,1998`; `services/memory/writer.rs:209`).
- Live wire `entries(after, limit)` returns `EntryPage { entries, more }`; `live()` snapshots via `attach(Some(u64::MAX))`. Command/job output pages cap reads at 1 MiB, return progress and base64 bytes, and offer stream-labeled chunk variants (`axo:crates/axo/src/session/wire.rs:11-27,118-228`). These are separate reads, not the native atomic attach contract.
- `Session::subscribe()` returns events from now on without a snapshot. Native `attach` still atomically captures missed entries, live state and receiver; receiver elements changed from `SessionEvent` to `Arc<SessionEvent>`. New serializable `SessionEventKind` and `kind()` support event selection; new `QueueChanged` requests a live queue refresh (`axo:crates/axo/src/session/mod.rs:258-265,327-377,474-482,3195-3208`). Axome directly consumes the old owned event type in `RelayState::apply`, and the relay passes receiver values into it (`Axome:src-crates/axome-core/src/services/axo/live.rs:494-505,885-899`). This is a concrete compatibility break, separate from whether Axome uses JSON subscriptions.
- `Axo::observe_child(id)` returns a receiver plus a residency cancellation token without reviving or retaining the child. Parking/removing/replacing a slot cancels that residency; cancelling one observer's child token does not cancel the session (`axo:crates/axo/src/axo.rs:324-335`; `crates/axo/src/session/children.rs:54-64,145-157,193-219`). Axome currently calls `Axo::session`, which revives a parked child, and owns `Arc<Session>` in `LiveSession`; observational-only access is a new capability, not a change automatically adopted by that path (`Axome:src-crates/axome-core/src/services/axo/mod.rs:542`; `live.rs:867-883`).

### One-off models and tools access

New native `Axo::models()` returns the shared registry and `Axo::supervisor()` its process supervisor (`axo:crates/axo/src/axo.rs:198-224`). New `CompletionRequest`, `Axo::stream(request,cancel)`, and `Axo::complete(request)` perform a model request outside any session, through the host-configured streamer. Selector resolution uses user model-role config without project config; the request carries messages, optional thinking/tier, token limit, temperature and tool choice. The complete collector preserves failure, usage and stop reason when the stream reports an error, or reports a terminal-less stream with no details (`axo:crates/axo/src/models.rs:18-101`). Models wire also offers lookup/list/provider metadata/credential-source/token-estimation methods (`models.rs:114-163`). No current Axome consumer of the new completion API; its memory capture still constructs a full agent session (`Axome:src-crates/axome-core/src/services/memory/writer.rs:246-272`). This API does not supply Axome's application-side session bookkeeping.

`ToolAccess` binds `Arc<SessionTools>` to a cloned `ToolContext`; it offers JSON invocation and `finish`, which waits for admitted file operations and adds authoritative `details.files`, converting failures with records into error outputs rather than discarding the records. Wire methods expose text/base64 reads and writes, command execution, scheme parsing/context/docs, ledger/snapshot/context access, artifact allocation and steering state. File reads are capped at 32 MiB on this wire path; native reads accept their own optional limit (`axo:crates/axo/src/tools/wire.rs:24-127,200-220,224-418`; `crates/axo/src/tools/writes.rs:214-298`). No current Axome `ToolAccess` consumer. Axome's existing web/browser/memory host factories receive `SessionTools`, so native file/command helper changes are a relevant adjacent surface (`Axome:src-crates/axome-core/src/services/axo/mod.rs:422-430`).

## 5. Other changed public contracts and behavior

### Agent/tool integration

- `Tool::prompt_guidelines` changes from `&[&str]` to `&[Cow<'static,str>]`: the returned list remains borrowed but supports dynamically owned guideline strings (`axo:crates/axo-agent/src/tool.rs:27-31`). Existing Axome implementations use the old signature: `src-crates/axome-core/src/services/axo/web/docs_tool.rs:94`, `web/search_tool.rs:98`, `src-crates/axome-core/src/services/memory/tools.rs:98`, and `src-crates/axome-browser/src/tool.rs:200`.
- Agent tool hooks are replaceable through `Agent::set_tool_hooks`; each before pass and each after pass takes its own immutable hook snapshot without holding the lock across awaits. Replacement between before and after can therefore affect the after pass; it is not a single snapshot for the whole execution (`axo:crates/axo-agent/src/agent.rs:164-180`; `crates/axo-agent/src/run.rs:647-650,823-827`). Axo installs fixed hooks followed by host/layer policies (`crates/axo/src/session/policy.rs:142-157,247-261`). Axome has no direct hook implementation today.
- `ToolContext` becomes cloneable and adds `on_hard_stop(recovery)`. After the 3-second cooperative stop grace, the loop drops the execution future and awaits an armed recovery future instead of aborting the task wholesale. Registration is native-agent task-local, is ignored outside that context, and duplicate registration panics. Native file mutations use this to retain mutation records after hard stop (`axo:crates/axo-agent/src/tool.rs:39-43,72-132`; `crates/axo-agent/src/run.rs:718-777`; `crates/axo/src/tools/wire.rs:129-179`). Axome's custom tools inherit the execution/cancellation contract; no current `on_hard_stop` consumer.
- `Agent::remove_queued` returns `(QueuedMessage, suffix_count)` and new `restore_queued` restores relative ordering after failed durable removal. `set_selection` installs model/thinking/tier under one lock; `AgentConfig` adds service tier. No direct Axome caller of these low-level queue/selection methods was found (`axo:crates/axo-agent/src/agent.rs:24-29,281-315,384-400`).
- Agent events, run outcome, cancellation reason, tool output/update and invocation IDs acquire serde/Specta representations; JSON uses camelCase tagged forms where specified. Native `AgentEvent` is still the inner event Axome maps into its protocol (`axo:crates/axo-agent/src/event.rs:10-19,58-70`; `agent.rs:68-81`; `tool.rs:47-50,176-197`; `Axome:src-crates/axome-core/src/services/axo/live.rs:677-717`).

### Errors, ordering and exports

`Error::Completion { message, details: Option<Box<CompletionDetails>> }` and `Error::SkillNotFound` are additions relative to the pinned base. The commit's “tuple→struct completion” breaking note describes an intermediate API in this range; base `5c3f418` had no `Completion` variant. `CompletionDetails` contains failure, billed usage and stop reason; `Error::code()` yields a serializable snake_case `ErrorCode`. Dispatch errors add unknown object/method, invalid arguments, encode, tool and no-session categories and preserve completion details (`axo:crates/axo/src/error.rs:5-13,42-50,114-191`; `crates/axo/src/ext.rs:96-162`). Axome's exhaustive `axo_error` mapper lacks the two new native variants (`Axome:src-crates/axome-core/src/services/axo/mod.rs:155-180`).

These are harness behavior changes under Axome's existing live prompt/queue/mode UI, not new responsibilities to reimplement ordering in Axome.
