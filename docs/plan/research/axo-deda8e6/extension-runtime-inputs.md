# Extension runtime inputs: run code on the host that owns the folder

2026-11-22 · axo `deda8e6` · Axome `48f5a03`  
**Question:** How should desktop and `axome-server` supply the extension runtime, isolate project contributions, and translate extension-initiated root lifecycles into Axome sessions and tabs?

**Decision in brief:** package Bun and own one manager next to each host's engine. A folder is a scope **within** that manager, not the current window, a global search root, or a second engine. This last part requires an axo change: `deda8e6` can ship the host-wide scope but cannot implement isolated project providers. Both parts use the same Axome session owner and Settings UI. Paths below prefixed `crates/` are axo; `core/` abbreviates Axome's `src-crates/axome-core/src/`.

## Host inputs

| Input | Supply this value on the executing host |
|---|---|
| `bun` | Both Nix launchers set an internal `AXOME_BUN` to `${pkgs.bun}/bin/bun`; read it once before restoring the child environment. The dev shell exports the same absolute path. For a raw source build outside that shell, resolve `bun` once against the host's base PATH (absolute directories only; never `.` or a project PATH). An explicitly supplied broken path is an error on that path, not an invitation to run a different binary. No editable Bun preference or automatic download. |
| User authored root | `dirs.config/extensions` (normally `~/.config/axome/extensions`), in the host scope. Each immediate package lives at `<root>/<id>/extension.json`. Put the runtime's authored packages here, not in the managed store. |
| Project authored root | `<canonical folder>/.axome/extensions`, only in that folder's trusted scope. Effective authored lookup is **user first, then this one project**. A repository cannot silently replace a user-authored implementation of an enabled id; report the duplicate and its paths. No sibling folders, ancestor discovery, active-tab shortcut or automatic directory creation in the checkout. |
| `data_root` | `dirs.data/axo/extensions/data`. Let axo partition host authored and installed ids. Project implementations need separate data (proposed below); neither changing a version nor closing a folder deletes its data. |
| `store` | Always `Some(dirs.data/axo/extensions/packages)`. This contains executable package versions, install records and rollback state; not user configuration, cache or package-private mutable data. **Not** `dirs.data/extensions`, currently occupied by Axome's separate language/harness format (`core/host.rs:79`; see the companion clash report). |
| `runtime_dir` | Private short host directory `$XDG_RUNTIME_DIR/axome/ext`; if unset, unsuitable or too long, allocate a random owner-only directory directly under `/tmp` and retain its `TempDir` guard for the manager lifetime. Never use a repository, a predictable shared `/tmp/axome` or a long profile/cache path for sockets. |
| `env` | One explicit `Arc<EnvMap>` derived from `EnvironmentService::current().base`, not raw GTK wrapper env, a connected client's env or `FolderExecEnv`. Strip Axome packaging markers and reserved `AXO_EXTENSION_*`; do not export Axome's credential store, login answers or protocol tokens. Give dependency scripts the same environment and ensure the packaged Bun's directory is available to scripts that invoke `bun` by name. Do not prepend Bun to the user's general terminal PATH. Installed/authored packages are trusted OS-user code, **not** a sandbox: base env can contain credentials/proxies and extensions can read host files. |
| `auto_install` | `false`. Missing/stale authored dependencies get **Install Dependencies** in the selected package's Settings row; show the reason/error and let the user run it. Never run lifecycle scripts merely because a folder opened. An explicit managed **Install** still performs its frozen install when required; neither install action means Enable. |
| Enabled list | Host's ordered **global** `axo.extensions: [{id, group?}, …]`, default `[]`. Extend Axome's validated `AxoSettings`, global-only layer policy and typed Settings writes; preserve order/group, don't alphabetize/deduplicate silently. Show enable/disable, reorder and group in the host's extension Settings (D4); `settings.jsonc` is backing storage. Trust admits a root, not everything in it: only user-enabled ids resolve. Group members in different scopes must not share a runner. |

`HostDirs` has config/data/cache but **no runtime**; even a relative XDG path currently survives (`core/dirs.rs:4-36,62-75,83-99`). Resolve server CLI overrides once against startup cwd as needed; require absolute paths at the extension boundary even when the target doesn't yet exist. Keep model caches under `dirs.cache/axo`, journals under `dirs.data/axo/sessions`, auth under `dirs.data/axo/auth.json`; no cache path belongs in `store` or `data_root` (`core/services/axo/engine.rs:33-55,76-83`; `core/services/axo/mod.rs:225`). Sharing XDG bases between two processes shares disk, not a live manager. axo has per-package advisory install locks but reconfiguration and the enabled check are manager-local (`crates/axo-extensions/src/store.rs:255-286,310-315`). For the default shared profile watch install-record changes as well as user settings and reconcile other live hosts; don't race uninstall against an enabled id in the global configuration. An independent server profile gets independent paths, not a copy of the desktop cache.

**Why pay for Bun?** `flake.nix:20-22,50-64` delegates frontend dependencies to bun2nix; `nix/pkgs/frontend.nix:32-48` consumes `bun.nix` to build assets. Neither that nor `pkgs.bun` in `nix/devshell.nix:19` is a runtime dependency. Add the path in the existing desktop wrapper (`nix/pkgs/axome.nix:84-98`) and server launcher (`nix/pkgs/axome-server.nix:60-67`). The local x86-64 `bun-1.3.13` output measured **132.3 MiB closure** (`nix path-info -Sh`, already installed; binary 100,900,512 bytes). That is a reference size, not a claimed download or incremental cost: Nix shares existing dependencies. The same binary/version for both hosts, independent of the shell that launched them, is worth this cost. Baked-in store paths alone would fail on non-Nix releases: distro desktop deliberately copies the unwrapped executable and rewrites its loader (`nix/packaging/desktop.nix:30-44`); the relocatable server creates its own launcher (`nix/packaging/server.nix:51-79`). Include a native/relocatable Bun payload and its required loader/libraries in these outputs and have their own launchers supply its actual absolute path; don't copy a store-dependent ELF and call it portable. No browser asset includes Bun.

Missing Bun does **not** prevent starting Axome, listing packages, editing settings or using ordinary non-extension sessions. Pass `None` for unresolved Bun, preserve invalid absolute-path diagnostics for an unusable configured binary, and show **Bun unavailable** with the looked-up path/repair action (restore package or install Bun for a raw build, restart host). Keep unavailable entries visible; don't claim an extension-shadowed provider or required policy will fall back. `crates/axo-extensions/src/lib.rs:76-97,637-654,883-897`, `process.rs:233-242`, `deps.rs:87-107`. Settings can show this in a host-captioned `SettingsSection`/`SettingRow`, like the resolved paths in `src/lib/features/settings/views/HarnessesView.svelte:1-21`; no new runtime setup wizard.

**Socket budget.** axo appends `/axo-ext-<random>/rpc`, binds a Unix listener and checks the full native byte length against **107**, not the displayed character count (`crates/axo-extensions/src/process.rs:83-96,245-253`). With six random ASCII characters the suffix costs 19 bytes: `/run/user/1000/axome/ext/axo-ext-Ab12Cd/rpc` is 43 bytes; a runtime root of 89 bytes would already fail. Reserve margin (e.g. cap the root at 80 bytes), validate an absolute owner-private XDG base and create its private subdirectory safely, else use the private short fallback. If that fails surface the setup error, not an insecure socket. Keep axo's final length check; don't depend on the tempfile default never changing. Axome has a short-path/private-dir precedent for its issue socket (`core/services/issue_bridge/socket.rs:12-39,47-65`); don't follow/chmod user-controlled symlinks in a shared temp directory.

## Session and host lifetime

Build `Arc<Extensions>` once in the lazily built `Engine` beside `Arc<Axo>`/`Models`, not inside a session, remote connection, renderer or Settings view (`core/services/axo/mod.rs:294-335`; P21 in `docs/plan/design.md`). Inherit the existing supervisor; desktop process group and server's configured process group/delegated cgroup work without another supervisor. Install a hook holding a **weak** `AxoService` reference. Subscribe to manager events, configure the initial validated list, then publish the fully initialized engine. An invalid extension configuration gets an extension-specific diagnostic and empty/last-good composition, not a broken base engine. No callback may recursively await the lock building that engine.

Use the global settings-change callback (`core/host.rs:96-105`; `core/services/settings_watcher.rs:25-54,92-107`) for ordered reconciles. Compare effective enabled lists; avoid resetting managers for unrelated settings writes. Treat invalid settings as invalid, not empty. Serialize/watch generations so an older reload cannot overwrite a newer edit; keep last-good on invalid edits. Prompt code-only edits use explicit Reload. After effective changes re-read affected live tool/command catalogs, provider views and manager snapshots; event stream lag also requires a snapshot. Don't rebuild or repopulate models from scratch.

For every ordinary root creation or open, finish host options (including tools, definitions, folder exec env and trust), then compose **before** axo starts the session. Register and attach each live root, including forks and recovered roots; deduplicate attach across the Axome path and Lifecycle's automatic attach. Subscribing a frontend is a different operation: Axome's `Held`/`LiveSession` owns residency and the chat stream. When retiring/closing a root, detach it before release; don't detach on the first window disconnect. Children are owned by axo, inherit the parent's composed snapshot at spawn and retain their root scope; do not open extra root tabs, recreate children or apply a second root layer to them. Explicit child inspection/subscriptions remain possible (`core/services/axo/mod.rs:493-590,628-658`; `crates/axo-extensions/src/session.rs:99-168,265-318`). On host exit reject new lifecycle work, settle admitted work before draining the registry, stop login, await manager `shutdown()` while sessions/runtime still exist, then finish session and supervisor teardown in the existing bounded shutdown path (`core/host.rs:321-324`; `core/services/axo/mod.rs:1834-1885`; `crates/axo-extensions/src/lib.rs:567-573,1235-1252`). Closing Settings, a folder, or the last remote client is not host shutdown.

**Login:** no `LoginInteraction` field belongs in `ExtensionOptions`. Use Axome's existing `Models::login(provider, &Interaction)` against the selected host/provider **view**. It already supports URL/instructions, device code, secret/plain prompt, selection and progress, one cancelable host login at a time (`core/services/axo/login.rs:122-168,178-205`; `crates/axo-extensions/src/proxy.rs:104-118,141-217`). Key, login, refresh and removal must all use the selected provider's origin-bound slot; retain the captured owner across a prompt, never redirect a stored secret to a new winner. Use the existing Providers dialog and host-routed login id/status/submit/cancel. For remote login only the asking client opens the HTTP(S) URL or displays the code; exchange/refresh and storage stay on the server. A client `localhost` redirect is not the server's listener: support the extension's device/paste flow when offered, otherwise explain the need for a tunnel, don't silently transfer tokens or invent a flow (`src/lib/features/settings/views/ProviderLoginDialog.svelte:30-42,58-103,134-177`). No prompt answered by broadcasting a secret to every viewer.

## Lifecycle: one root operation, one owner, one tab identity

The SDK supplies an extension namespace, **not** a source window, active folder or mandatory parent session (`crates/axo/src/ext.rs:16-20`). Implement the four async methods in `core/services/axo/` over the same primitives used by `operations/chat.rs`, not by invoking frontend commands or block-on RPC wrappers from inside the runtime. Refactor create/load/fork to return the held `Arc<Session>` and metadata internally; existing commands can still project ids. Preserve opening/retiring barriers and the folder check. Scope identity is `(execution host, canonical folder, root session id)`, not a displayed tab id.

| Hook | Operation and observable result |
|---|---|
| Create | Require an absolute existing `cwd`, canonicalize on the executing host (`core/services/folders.rs:5-15`); **that exact folder owns this root**, even for a subfolder/worktree or when no tab exists. Build normal host defaults there, honor explicit `model`, `agent`, `thinking`, `sections` and cap `project_access` at the host's actual D4 trust (a caller may request less, never more). Register root, event pump and tab intent; return the retained session. Never use the active client's folder or let a repo enable itself. |
| Open | Resolve the requested journal against the executing host's session store, read its header before selecting tools/trust/roots, validate the stored id/path and canonical `header.cwd`. The journal directory is **not** the folder. `Axo::open_session` rewrites cwd from that header and rejects child journals (`crates/axo/src/axo.rs:256-285`): returning child-as-root is wrong. Return the already-live root only when id/path/folder match; don't silently reconfigure an existing session with inconsistent request overrides. Otherwise wait for retirement, open with target-folder options and register. Reuse the existing tab or insert the chat tab directly, including if it is the folder's first tab. |
| Fork | Reuse the source session/entry fork primitive, track the fork as a new independent root **in its source's owning folder**. Keep Axome's memory capture cursor behavior and the editable prompt parts from the fork; route the parts to the new tab as an unsent draft and return the SDK `Forked` receipt (`core/services/axo/mod.rs:1704-1754`; `crates/axo-extensions/src/lifecycle.rs:126-141`). Resolve ownership from the source/root registry or journal for an observed child; never borrow the requester's focused tab. |
| Close | Close the **root session**, not merely its visible subscription and not its journal/history. Resolve one target id; reject a child id on this root hook. Use `AxoService::close`/retirement: stop root/descendants, notify observers, await release, retain written history/memory capture (`core/services/axo/mod.rs:762-780,1059-1082`; `live.rs:990-1019`). Remove every view of the closed root; child views must close or switch to read-only history, not silently revive the root. No deletion, no closing another folder's tabs, no second backend close from the renderer applying the event. If unrelated tabs remain the folder stays open; if the last disappears the normal claim is released. Idempotent on repeated close of a known closed root; report an unknown target accurately. |

**Tab delivery is not the summaries feed.** Today `register` emits `ChatSummariesChanged`, remote events filter these to *already claimed* folders, and `openChatSession` activates or inserts a matching tab in the calling workbench. A folder is open precisely while there is a tab: committing the first/last tab claims/releases it (`core/services/axo/mod.rs:592-613`; `src-crates/axome-server/src/events.rs:98-117`; `src/lib/features/sessions/service.svelte.ts:96-103`; `src/lib/features/workbench/state.svelte.ts:1-7,158-182,218-222`). In an unopened folder the chat **is** the first tab. No invisible project record, empty preview tab or mandatory switch of focus.

Use a typed, idempotent **workbench tab operation** (ensure/remove by root identity, title, optional editable draft) with a monotonically ordered revision. Persist pending operations on the host until a snapshot including that revision is acknowledged. An event wakes the designated controller; replay after attach/reconnect/lease takeover. Don't let a stale debounced snapshot resurrect a closed tab or overwrite a new one (`src/lib/features/workbench/persistence.ts:1-5`; `src-crates/axome-server/src/workbenches.rs:504-539`). Prefer an existing root's owning workbench, then one owning the target folder, then the originating workbench if known. Otherwise pick the host's most recently used eligible workbench with stable id tie-break; if none exists assign a durable default workbench. Create/open/fork present **once**, in background by default; close reconciles all owners. Never present once per connected browser/window or send to a different machine that happens to have the same path. Desktop applies via the normal tab reducer; web/remote uses the server workbench id and its existing controller lease (`src-crates/axome-server/src/server.rs:523-551`; `workbenches.rs:1-2,541-548`). Folder-claimed events alone cannot deliver the first tab. A host-side operation may finish without any UI online.

Keep a real residency pin for an extension-created/opened root until presentation transfers ownership or explicit close; an unattached written root can retire immediately, an unwritten one after the ordinary grace period (`core/services/axo/mod.rs:208-214,644-657,670-695`). An extension must be able to call the session id it just received even with no controller. On reconnect replay the committed intent, including the fork draft. A pending tab does not make a journal durable: `JsonlWriter` deliberately doesn't create a file for an empty root (`crates/axo/src/store/jsonl.rs:385-391,420-447`). To promise stable receipts across **host restart**, request explicit materialization of a root's existing header before committing its durable tab intent; never manufacture a conversation turn to force a write. Until materialization exists, an empty root's id is valid for that host lifetime only; reconcile a missing empty root as a new empty chat on restart, not a phantom live session. Keep UI connection loss distinct from server process death.

Preserve Axome's existing user protections. A locked tab/unsent editable draft isn't permission to discard it; where existing close policy requires consent (active jobs/children, protected work), route one request naming the extension and affected work to the controlling UI, recheck identity on reply, and on decline/unavailable controller return a concrete error **without stopping anything**. Keep drafts if the closed session had other viewers. Idle, unprotected roots close without a prompt. Put the decision *before* teardown, never ask after `evict`; the projection of a successful close must not call the destructive command again (`src/lib/features/workbench/tabActions.svelte.ts:29-58,80-86,118-150`). Record and finish an admitted operation once even if the calling runner disappears; don't hold a registry/config lock waiting for a renderer or a runner. axo already completes the hook independent of caller cancellation and attaches the returned session/detaches after successful close (`crates/axo-extensions/src/lifecycle.rs:37-41,93-151`).

## Proposed axo handoff

**The counterexample:** folders A and B have independently enabled authored code with the same id in different checkouts (the enable list itself is user-only). `ExtensionOptions.roots` is stored once by `new`; `configure` accepts *only* the enabled list. `locate` takes the first matching path, even if unreadable; `compose` does not inspect folder/cwd, `attach` applies one manager-wide list, `reapply` visits every attached root. Meanwhile `new` allocates a provider layer on the **shared** `axo.models()`, where the newest containing layer wins. One union of roots makes A's tools/hooks and provider available to B; two managers on one engine can separate tools but **not** providers, credentials, or requests. Focus changes cannot fix concurrent turns. These are runtime semantics, not a Settings filtering problem (`crates/axo-extensions/src/lib.rs:76-96,362-400`; `manifest.rs:206-247`; `session.rs:99-118,265-318`; `crates/axo-ai/src/models/mod.rs:516-548,814-847`).

Propose these contracts, not Axome types in axo:

1. **One manager, explicit scope handles.** Keep `ExtensionOptions.roots`, store, user/installed placements and ordered enable list on the host base. Add a caller-supplied opaque scope id and ordered additional roots, e.g. `extensions.scope(id, roots)` returning a handle for `compose`, `attach`, effective status/collisions and scoped retry/reload/dependencies. `configure` validates once; reconcile base and active scopes without cross-applying. Resolve each enabled id once *per effective scope* in the original order (host authored then additional roots; installed ids only via store). Reuse identical base packages/runners across scopes; key project placements, failure budgets, group ids, event subscriptions, package state and diagnostics by scope + origin. Same project id in two different checkouts must not share a data directory: give the scope a separate root such as `data/projects/<stable hash of canonical folder bytes>/<id>`. A group mixing scopes splits by effective origin scope; show this in Settings. Never treat a missing project-only package in the base as a broken install in every unrelated workspace; status should identify where an id resolves or is absent.
2. **Provider views, not global project provider registration.** Add a cheap read/request view over one P21 registry: shared loaded catalog, feeds, timers, auth store and user/installed providers; scoped ordered provider winners/reservations are visible only to the corresponding view. A scoped package must not call global `ProviderLayer::replace` as its publication mechanism. Preserve last-enabled-wins *within the merged scoped list*, not unconditional project-wins. Thread that view through root and child model selection, request execution, completion/stream, provider listing/login/key removal, scoped `models.*` SDK calls and Axome's folder-aware model picker/catalog. Host-only consumers see the base view. Resolve each request against one captured winner/credential origin so changes in B (or incoming config edits in A) can't switch A's in-flight key. Global provider Settings shows global origins; inspecting A's project provider requests A's view explicitly. Keep owner/path credential isolation (`crates/axo-ai/src/models/mod.rs:294-324,597-657`; `crates/axo-extensions/src/lib.rs:1152-1164,1293-1300`).
3. **Target-bound composition and lifetime.** Record scope on attachment; reapply affected roots only. Child spawn/fork takes the source root's scope; resolution of a known child does not create a project-global attachment. Route implicit Lifecycle attach using the **returned root's host-selected scope**, including A's extension creating a B root. For example the hook returns `(Arc<Session>, ScopeHandle)` (and scope with `Forked`), and the manager does exactly one target attach. Pass opaque calling scope alongside the extension namespace for diagnostics and authorization, not a fake caller tab id. A project extension's automatic journal observers/subscriptions shouldn't get unrelated roots; explicit cross-folder lifecycle operations use the target's policy. Scope shutdown fences callbacks, retires its provider overlay/runners and clears root layers without touching base or B. Keep the stable scope until the last live root/child or management operation releases it; changing the focused tab is not a lifetime signal. For durable external lifecycle receipts also expose an explicit writer/materialize operation; tab persistence remains in Axome.
4. **Trust lives outside the API.** Axome maps canonical folder → opaque scope on actual workbench use or target-session creation. Restricted folder: no extra roots at all, no project discovery/activation/dependency install; use D4's restricted `ProjectAccess` ceiling for all session/catalog paths, including `default_persona`. Trusted folder: exact root only; no Settings permission for a project to add itself to the global enable list (`crates/axo/src/config.rs:73-160,659-677`). Trust/untrust reconciles affected scopes, including inherited parent/worktree changes. On revoke deny new work first, retire affected project placements/installs and fence old proxies; existing children have snapshots, so end/reopen affected trees under restricted access rather than leaving executable old registrations behind. Notify before trust revocation stops active work. Don't rely on detach alone: it leaves registrations in place. A disabled/restricted runner can't be made safe by filtering tool names after the fact. The admission gate limits what Axome loads, not what already-running trusted Bun code can do as the OS user (`process.rs:109-118`; `deps.rs:87-105`).

D4's **Trust Folder / Manage** banner, persistent restricted status, and parent/worktree inheritance are the single source of authority on each host; **not implemented today** (`docs/plan/design.md`, D4; `TODO.md:10`; unconditional trust in `core/services/axo/mod.rs:428-439,923-935`). Use the same gate for project root admission and settings writes, not a second “trust extensions” toggle. Like [VS Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust), the point is preventing automatic project execution before trust. Like [VS Code's workspace extension host](https://code.visualstudio.com/api/advanced-topics/extension-host#preferred-extension-location), executable code belongs where the workspace is, not where the UI renders. Unlike VS Code, axo needs **no** extension-host location selector, picker, window, trust list, database schema or tab type: clients supply roots, scope identity and target attachment; axo owns composition, provider resolution and process lifetime.

**Acceptance cases for the handoff:** two trusted folders with the same extension id/provider produce distinct tool responses, credentials, persistent data and model requests concurrently; host-only requests see neither project provider. A restricted B remains unaffected while A installs/reloads or is revoked. A → B lifecycle create, open and fork use the target's tool and model views; closing A cannot retire B or host packages. Disconnected remote presentation replays once into the correct workbench and closing the last tab releases the folder. These are proposed checks, not claims of executed tests.

## Recommendation

1. **Ship the host-wide slice on `deda8e6`**: package Bun in every distribution, adopt the path/env table, persist user enablement, wire one engine-owned manager, use existing login and add the four host lifecycle operations plus durable client presentation. User-authored and installed packages (including providers and session contributions) work without project roots. Keep project roots absent, not “disabled after loading.” Label that delivery as the host-wide slice, not completion of full extension support.
2. **Deliver full project support with the scoped axo contract and D4 gate.** Share engine/store/supervisor, never the project contribution or provider overlay. The same axome-core logic runs against `axome-server`'s effective `--config-dir`, `--data-dir`, `--cache-dir`, service-user environment and filesystem. A remote install selects a server-local source; the client supplies typed intent, displays host-captioned status and answers login. It does not send its Bun path, XDG paths, trust list or credentials to “bootstrap” the server (`src-crates/axome-server/src/main.rs:69-109`).

**Rejected alternatives**

- Manager per folder on one registry: provider winners and authentication still bleed between concurrent folders; also duplicates base runners.
- Second engine per folder: separates providers by duplicating P21 registry, feeds, session ownership and startup work.
- Recreate/reconfigure on focus or union all trusted roots: incompatible with parallel sessions/headless callbacks; opening one repo changes another session's code.
- Skip project extensions as the end state: fails full support. Gating until the handoff is a release sequence, not the design.
- User-set Bun path or PATH-only production lookup: version/drift and GUI/service PATH differences become first-run failures; one more host setting without a product benefit.
- Automatic installs on folder open: executes dependency scripts before an explicit package-management action.
- Per-window managers or fire-and-forget “open tab” broadcasts: duplicate effects on multiple clients and lose them on disconnect or on an unopened folder.

## Needs Toph

None. Full support, root lifecycles, one registry per host, D4 trust and complete Settings coverage already determine the important boundaries. The axo handoff is an engineering dependency, not a product decision.
