# Providers, credentials, registry, and service tiers

- axo revision: `deda8e6`; comparison base: `5c3f418`.
- Axome HEAD: `48f5a03`.
- Date: 2026-11-22.
- Question: What changed in axo-ai and axo's model-facing surface, what does axo own, and which existing Axome consumers are affected?
- Evidence: source inspection and revision diff only; no builds, tests, live provider calls, or credential migration performed. Paths beginning `crates/` are in axo at the target revision; `src-crates/` and `src/` are in Axome at the stated HEAD. This is an inventory, not an adoption design.

## Credentials: origin-bound storage

The credential store remains an opaque string-keyed JSON object, not a provider registry. `get`, `set`, `remove`, and locked `update` address exactly the supplied key; they do not translate provider ids or migrate older entries (`crates/axo-ai/src/auth/store.rs:119-175`). File writes retain exclusive locking and atomic replacement; the slot format is assigned by the registry, not the file store (`auth/store.rs:15-19`; `models/mod.rs:294-324`).

| Provider source | Credential slot | Meaning |
|---|---|---|
| Built-in Codex / models.dev provider | `loaded/{id}` | Loaded origin, including built-in login. |
| Provider added or patched by models.jsonc | `loaded/{id}` | The same loaded namespace; config is not a separate contributor owner. |
| Host `Models::register(owner, provider)` | `registered/{owner}/{id}` | Caller-supplied stable contributor identity; nonempty. |
| `ProviderLayer::replace` entry | `layer/{owner}/{id}` | Per-entry stable owner; layer ordinal controls precedence, not credential identity. |
| Extension bridge provider | `layer/extension/{extension-name}/{hex-package-path}/{provider-id}` | Bridge constructs the owner from the extension name and encoded package-path bytes. |

Sources: `crates/axo-ai/src/models/mod.rs:294-324,516-548,814-847,982-996,1034-1044`; `crates/axo-extensions/src/lib.rs:1152-1164,1293-1300`. The package path contributes to credential identity: changing that path changes the slot even if the extension/provider names do not.

“Origin” is the loaded / registered / layer category; “owner” is the contributor identity within runtime categories, not an account id or the layer's creation sequence (`models/mod.rs:92-110,516-520`). The newest layer containing an id wins, then the registration, then loaded state. Registrations replace the entire provider definition: loaded models, environment names, config key, headers/overrides and built-in login are hidden (`models/mod.rs:516-539,659-717`). Consequently two contributors using the same provider id do not silently inherit each other's stored login. Reusing the same kind/owner/id intentionally reuses a slot; this is contributor isolation, not per-instance isolation. The API validates nonempty owners and nonempty slash-free provider ids; it does not authenticate owner claims (`models/mod.rs:294-310,333-361`). Hosts supply their stable owner identities.

Old bare-provider entries are **ignored by registry authentication, not deleted or migrated**: lookup uses only `info.slot`, and the file store has no fallback (`auth/resolve.rs:121-135,167-200`; `auth/store.rs:121-147`). Existing logins therefore need re-establishment under the new slots; old entries remain in the file. Environment and config keys remain usable.

`Models::credential_slot(provider)` exposes the current opaque slot, including unavailable winners. `credential_source` also works for unavailable winners and reports precedence **config presence → stored API key/OAuth → first nonempty configured environment variable → none**. It neither resolves config strings nor refreshes/validates credentials (`models/mod.rs:597-610,659-672`; `auth/resolve.rs:121-135`). A config key's presence can therefore report `Config` even if later interpolation fails. Actual auth resolves headers/config, refreshes expiring OAuth within five minutes using the same slot under the store lock, preserves config header/base-URL precedence over OAuth values, and rejects missing required keys (`auth/resolve.rs:140-249`). Login captures an origin-specific auth record and writes its slot even if registry precedence changes while the interaction runs; only still-visible loaded Codex login triggers account discovery (`models/mod.rs:620-643`).

### Axome credential consumers

- Axome constructs one `FileCredentialStore` at `dirs.data/axo/auth.json` (`src-crates/axome-core/src/services/axo/mod.rs:225`) and passes it into `Models::load` (`engine.rs:26-55`). The filename/location remains host-owned and unchanged by axo.
- **Behavioral break not merely a compiler error:** `provider_set_key` writes the bare provider id and `provider_remove` removes the bare provider id (`providers.rs:63-85`). Under the new registry those writes are invisible to model auth, and removal no longer removes a newly logged-in credential. The store trait signature still accepts strings, so these calls can compile while doing the wrong operation.
- Login already calls `Models::login`, so it will write the new slot automatically (`login.rs:202-205`). Provider source/status UI already calls registry `credential_source` and probes registry auth (`providers.rs:17-42`; `mod.rs:798-806`), hence sees old logins disappear and reports unavailable-provider errors through its existing generic error branch.
- Dedicated web-search keys are **not model credentials**: `web:parallel`, `web:tavily`, `web:exa`, `web:brave`, `web:perplexity` remain direct opaque store keys (`web/auth.rs:15-64,126-139`). No axo key migration applies to them.
- Grounded search does use registry auth (`web/providers.rs:112-143`), so origin selection, ignored legacy credentials and provider unavailability apply there too. Its wire requests are Axome-owned, not axo-ai adapter requests; tier support in axo does not automatically add a tier to those requests.
- Providers Settings states removal affects stored credentials only and displays config/env sources (`src/lib/features/settings/views/ProvidersView.svelte:75,243`); this intended distinction remains, while the backend bare-id removal no longer reaches the relevant model slot.

## Registry: ownership, publication, and discovery

### Runtime provider surface

`Models::register` now requires an owner and validates before modifying state. `unregister(provider)` still removes a registration by provider id, not owner, reveals loaded state, and does not delete credentials. In-flight requests retain captured model/provider records; future requests re-resolve provider/id (`crates/axo-ai/src/models/mod.rs:516-539,675-717`). No current Axome production caller registers providers or owns a provider layer; its construction is loaded-catalog based (`src-crates/axome-core/src/services/axo/engine.rs:47-84`).

`ProviderLayer::replace(Vec<(String, Provider, Option<String>)>)` validates all entries before publishing any: nonempty owner, valid provider id, model/provider identity agreement, distinct model ids, no standard-tier multiplier, no duplicate provider ids across entries. Failure leaves the previous layer intact; an empty list removes its entries. Dropping a layer reveals lower precedence state (`models/mod.rs:333-361,814-895`). A reservation can keep models listed while marking its provider unavailable. `auth`, requests and login then fail before credential lookup; metadata and credential source remain readable (`models/mod.rs:597-610,659-689,850-864`). `hidden` reports the category underneath a layer, not a credential (`models/mod.rs:867-884`). Axome has no current layer-management consumer, but its catalog filters models whose provider auth fails (`mod.rs:809-825`), so reserved models would be absent from its available-model list while still counted in Providers.

### Transaction boundaries and retained state

- `reload` constructs a candidate loaded registry before assigning config, extended-context setting, loaded state, or restarting the timer. Build error leaves those unchanged (`crates/axo-ai/src/models/mod.rs:453-484`). Axome already exposes last-good-state behavior on reload and falls back to built-ins on initial load failure (`engine.rs:61-72,89-104`).
- Refresh fetches catalog and Codex feeds concurrently, builds the candidate, then commits feeds/caches and publishes the snapshot (`models/mod.rs:149-194,793-810,897-931`). Candidate build failures leave published feeds/state uncommitted. Cache-write errors are warnings, not an all-or-nothing disk transaction. A **catalog fetch failure can still publish useful Codex/discovery changes and return an error**: the old catalog is reused in the candidate and `pending.commit` propagates the catalog error after assigning Codex input (`models/mod.rs:149-194,793-810`). Thus “refresh returned Err” does not universally mean “nothing changed.”
- Custom OpenAI-completions discovery runs only for new config providers with base URL and no explicit `models` list. It checks whether a runtime provider hides it before auth and again before the HTTP request; a hidden or failed discovery preserves previous ids. Independent discovery calls are concurrent (`models/mod.rs:1023-1074`; `models/discover.rs:26-57`). The checks prevent initiating hidden-origin auth/network activity at those boundaries, not revocation of already-started HTTP.
- Empty/unusable downloaded catalogs are rejected (`models/mod.rs:919-931`). Codex rows without positive context windows are excluded; account `service_tiers` and `additional_speed_tiers` feed supported tiers (`models/codex.rs:119-137`).
- `lookup(provider,id)` returns an `Arc<Model>`; the current snapshot and indexed lookup share model allocations (`models/mod.rs:197-245,560-569`). Axome's existing `all()`/`find()` consumers remain its catalog/context-window path (`engine.rs:18-21`; `mod.rs:798-825`).

## Service tiers: capability, selection, persistence, billing

`ServiceTier` is `standard` (default), `flex`, `fast`, `ultrafast`. `Model.service_tiers` maps supported nonstandard tiers to USD price multipliers. `Model::effective_tier` returns the chosen tier only when declared supported, and for Anthropic Messages only `fast` is sendable; otherwise it returns standard (`crates/axo-ai/src/types.rs:379-436`; `model.rs:69-76,112-128`). Chosen versus effective tier is deliberately separate: a session can remember an unsupported chosen tier without sending it.

### Where support and prices come from

- models.dev `cost.multipliers` supplies recognized tier factors, including scalar or `factor.text`, finite positive checks, and date conditions (`lt`/`gte`). If absent, input-price tier overrides can derive a whole-table multiplier from `tier input price / base input price`; the source explicitly notes this approximation (`models/rules.rs:370-437`).
- Codex account discovery supplies availability from `service_tiers[].id`, with `additional_speed_tiers: ["fast"]` adding `priority`. The matching models.dev OpenAI row supplies multipliers; advertised tiers without a matching factor receive **1.0**, not a hardcoded surcharge (`models/codex.rs:119-137`; `models/rules.rs:465-518`).
- `models.jsonc` model definitions and model overrides accept `serviceTiers`. Entries merge by tier, `null` removes a tier, standard is rejected, and factors must be positive finite numbers (`models/config.rs:77-103,159-177`). Programmatic providers expose the map directly; their registry validation rejects standard but does not apply the config parser's finite-positive multiplier validation (`models/mod.rs:333-361`).
- Base/context-window price tiers remain distinct from service tiers. Cost first selects context rates, then multiplies all components, including cache writes (`cost.rs:1-42`).

### Selectors and commands

A selector can name a model or `@role` with one thinking suffix and one tier suffix in either order, e.g. `provider/model:high:fast`, `@role:flex:low`, or suffix-only `:fast`. Explicit role suffixes override suffixes in the role's stored selector. Exact model-id lookup is attempted before stripping up to two suffixes, preserving models whose ids contain colons; duplicate thinking/tier suffixes are rejected (`crates/axo/src/config.rs:287-385`).

`/tier` is a built-in `Alongside` command with an enum-valued `tier` argument, applied from the next request (`commands.rs:154-159,186-192,291-297`; `session/mod.rs:2771`). `Session::set_service_tier` chooses/journals a tier and returns what the current model effectively applies; `service_tier()` returns chosen and `effective_service_tier()` returns sendable (`session/mod.rs:2462-2472,3148-3159`). This does not require a new session or the host to implement provider-specific transport.

### Session policy and durable records

- `serviceTier.onModelChange` defaults to `reset`; `keep` retains a chosen tier when changing models. Same-model switches retain it and an explicit selector tier always wins (`config.rs:199-231`).
- `subagents.serviceTier` defaults to `standard`, optionally `inherit`; a tier explicitly selected by the child model cascade takes precedence (`config.rs:174-195,234-240`; `session/spawn.rs:429-447`). Both `subagents` and `serviceTier` are user-only settings; project layers cannot set them (`config.rs:670-677`).
- Tier mutation uses the selection ordering lock, appends durable records before applying live state, and coalesces a simultaneous thinking+tier change into `ThinkingLevelChange.service_tier`; tier-only changes use `ServiceTierChange` (`session/mod.rs:1385-1426`; `store/entry.rs:319-324`). Journal wire naming is `service_tier_change` (`session/journal.rs:21`).
- Projection restores the latest tier, including the thinking-change field (`store/project.rs:128-140`). Reopening feeds that projection through model-change policy (`axo.rs:492-518`). Mode restore captures/restores the previous chosen tier with model/thinking (`session/modes.rs:203-257`).
- Host-visible surfaces are session journal `SessionEvent::Entry` broadcasts, persisted assistant messages, and `LiveSnapshot.service_tier` during attach; no dedicated registry-tier change signal is introduced (`session/journal.rs:141,279-285`; `session/mod.rs:3240-3248`; `axo-ai/src/types.rs:99-102`).
- Compaction requests construct `SimpleStreamOptions` with thinking/max tokens/tool choice/session id and default the rest, so tier stays standard even if the chat chose a premium tier (`compaction/summary.rs:370-380`).

### Transport and accounting

OpenAI-family adapters send `flex`, `priority` for fast, or `ultrafast` in `service_tier`; standard omits the field (`axo-ai/src/api/mod.rs:87-105`; `api/codex.rs:183-187`; `api/completions.rs:330-334`). Anthropic sends `speed: "fast"` and the fast-mode beta within its existing beta-feature logic (`api/anthropic.rs:640-645,746-752`). Unsupported tiers are reduced by `effective_tier` before transport.

Adapters initialize `AssistantMessage.service_tier` to the effective requested tier, then use provider echoes when present (Anthropic usage `speed`, Responses `service_tier`, Completions chunk `service_tier`). Unknown echoed strings map to standard (`api/anthropic.rs:200-207,324-340,356-381`; `api/responses.rs:714-722`; `api/completions.rs:1133-1136,1242-1273`; `api/mod.rs:97-104`). Cost uses the served tier and `model.service_tiers.get(tier).unwrap_or(1.0)` (`cost.rs:26-42`). Messages retain the served tier and computed monetary components; **there is no separately persisted multiplier field in `Usage` or `AssistantMessage`** (`types.rs:80-115,259-304`).

The old Codex post-response hardcoded flex 0.5 / priority 2.0 (2.5 for gpt-5.5) adjustment was removed by this revision range; the new shared Responses cost path uses registry factors (`api/responses.rs:714-722`; `cost.rs:26-42`; comparison diff of `api/codex.rs`, removed `apply_service_tier_pricing`). [INFERENCE] Newly recorded cost totals can differ for otherwise equivalent tiered usage when feed factors differ or are missing. This does not retroactively recompute old persisted usage.

## Other adapter and public-type changes

- `Model` adds `service_tiers`; `SimpleStreamOptions` adds `service_tier`; `AssistantMessage` adds `service_tier`, serde-defaulted and omitted when standard. Rust struct literals require the new field even though old serialized messages can default it (`axo-ai/src/model.rs:69-76`; `api/mod.rs:73-85`; `types.rs:99-101`). Axome's assistant-message test literal is at `src-crates/axome-core/src/services/axo/convert.rs:1231`; its model fixtures also construct upstream models. Compilation coverage belongs to the separate compile probe.
- `Usage` gains **no new data fields** in this range; its change is Specta type support. Existing token and dollar fields remain (`types.rs:257-304`). Models, credentials, messages/content, API kind, thinking and tool-choice types also acquire serialization/type-export support for the extension bridge; input content's string-or-block-array/null representation is described separately from output block arrays (`types.rs:471-496`; `auth/mod.rs:30-49`; `api/mod.rs:53-62`). Axome currently has its own protocol projections, not a direct consumer of these generated wire types.
- New `axo_ai::Error::ProviderUnavailable { provider, reason }` produces structured failure code `provider_unavailable` with `should_retry: false`. HTTP rewrite setup preserves that typed failure before converting errors to strings (`error.rs:27-42`; `api/http.rs:100-130`). Axome Providers already routes non-missing-key auth failures into its generic error status (`providers.rs:32-37`).
- HTTP prepared bodies use `bytes::Bytes` instead of `String`, eliminating per-retry full-body copies (`api/http.rs:95-130`). No direct Axome consumer; behavior remains within adapter transport.
- Codex adapter no longer independently requires a token: it can build requests without one for providers whose registry policy permits it. It derives the account header only when a token exists; a present API token is applied after configured headers, while protocol headers remain protected (`api/codex.rs:81-126`). Registry `requires_key` still gates built-in auth (`models/mod.rs:988-995`; `auth/resolve.rs:203-207`). This enables keyless/header- or rewrite-authenticated runtime providers, not keyless built-in Codex access.
- New `Axo::stream(CompletionRequest, cancel)` / `complete` resolve user roles, thinking/tier overrides and run a one-off request through the configured streamer, independently of a session. Completion failures use structured `Error::Completion { message, details }`, preserving failure/usage/stop reason when a terminal error message exists (`crates/axo/src/models.rs:18-100`). Extension-facing `models.find/all/providers/credentialSource`, token estimates and `complete` expose model services without returning raw credentials (`models.rs:114-164`). No current Axome consumer of this new one-off API; Axome grounded web requests are a separate native-search integration.

## Axome surface gaps and existing behavior

1. **Model catalog/protocol:** available models currently publish selector/provider/name/thinking/context-window/images, not tier capabilities or multipliers; roles/default-model projections reduce choices to model id and thinking (`src-crates/axome-core/src/services/axo/mod.rs:809-825,850-896`). Axo now provides chosen/effective tier and supported tier metadata; Axome has no equivalent projected field here.
2. **Picker and role selector syntax:** Axome's shared `splitSelector` recognizes exactly one trailing thinking suffix and `joinSelector` appends thinking only; its role-name validation accepts no suffix (`src/lib/features/chat/elements/model-picker/selector.ts:15-47`). The picker resolves model/effort only and matches roles by exact `@name` (`ModelPicker.svelte:71-94`). Thus axo's two-suffix and role-tier syntax exceeds the UI's interpretation even where custom selector text can be stored. No UI behavior was exercised.
3. **Settings:** Axome uses its own deny-unknown-fields `AxoSettings` schema, currently without `serviceTier` (`src-crates/axome-protocol/src/axo_settings.rs:9-35`); its Models view edits modelRoles/defaultThinkingLevel (`src/lib/features/settings/views/ModelsView.svelte:34-78`). Axo's settings acceptance does not by itself add Axome settings controls or protocol acceptance. `models.jsonc` is separately parsed by axo's `ModelsConfig`, so its new `serviceTiers` patches reach the existing file load/reload path (`engine.rs:96-114`).
4. **Session events:** Axome explicitly handles model/thinking journal selection entries (`src-crates/axome-core/src/services/axo/live.rs:596,631`; `mod.rs:2133`). The additional tier record and thinking-change field touch those projections; Axome currently has no tier-specific state/control. Command schema conversion is generic enough to transport built-in parameter schemas, but the updated upstream command-policy contract is a separate breaking change (`convert.rs:84-98`).
5. **Costs:** Axome projects `Usage.cost.total` to a scalar and displays totals in ContextPanel and subagent AgentBlock (`convert.rs:134-142`; `src/lib/features/chat/sidebar/ContextPanel.svelte:309-312`; `src/lib/features/chat/elements/transcript/AgentBlock.svelte:116,359`). New adapter-computed tier costs therefore flow through existing numeric totals, but the UI receives neither a tier label nor the multiplier explanation. Unknown cost still looks numeric, not unknown.
6. **Host ownership:** Axome still supplies paths, store, cache, config source, Models construction, list-refresh events and frontend projections (`engine.rs:26-84`; `login.rs:213-225`). Axo owns origin resolution, registry precedence, tier interpretation/transport, journal selection and per-response pricing. The new extension layer and one-off model API create capabilities with no current Axome wiring; no adoption choice is selected here.
